Goal

Make actuals and MTM advance together as one coherent state.

Whenever the existing actuals refresh detects a newly finalized or materially changed NFL game:

1. update realized Calcutta actuals;
2. calculate the corresponding live/provisional MTM update;
3. publish both together;
4. make every UI/API surface read the same resulting current MTM.

Do not create a separate polling cadence for live MTM. Use the existing actuals refresh as the trigger.

Do not rerun the full season simulation after every game. Use the existing conditional/live valuation outputs from the latest successful full simulation wherever possible.

⸻

1. Establish one authoritative current-MTM read model

Create one shared server-side function/service for resolving the current displayed MTM for a Calcutta.

It should return, for every team:

* current MTM / gross value;
* net MTM where applicable;
* ownership-adjusted value where applicable;
* last full-simulation MTM;
* whether the current value is official or provisional/live;
* source full-simulation snapshot ID;
* current actuals/live-state version ID;
* as-of timestamp;
* games incorporated into the live adjustment;
* stale/pending status and reason, if applicable.

All consumers should use this read model rather than independently selecting snapshots or calculating provisional values.

Consumers include:

* Live Tracker bar chart;
* Live Tracker team table;
* Results MTM column;
* owner/portfolio totals;
* normalized valuation endpoints;
* MCP/API responses exposing current MTM.

The basic rule should be:

current displayed MTM = latest valid live/provisional valuation if available, otherwise latest successful official simulation MTM

⸻

2. Use the actuals refresh as the live-MTM trigger

Extend the existing actuals refresh workflow rather than creating a parallel job.

Target flow:

refresh actuals
→ fetch/update game results
→ determine whether anything economically relevant changed
→ calculate realized Calcutta actuals
→ calculate live MTM adjustment
→ validate both
→ publish one new coherent state

Only trigger the MTM portion when relevant game state actually changed.

Examples:

* game becomes final → yes;
* corrected final score → yes;
* marquee classification/result changes → yes;
* polling again with identical game data → no;
* halftime score changes → no, unless the product intentionally supports intragame MTM later.

For the current implementation, treat finalized/corrected games as the relevant trigger.

⸻

3. Track an explicit actuals/live-state version

Introduce or reuse a durable version/snapshot record representing the state produced by an actuals refresh.

Each version should identify:

* Calcutta/pool;
* season;
* timestamp;
* source official simulation snapshot;
* incorporated finalized game IDs/results;
* actuals version;
* live/provisional valuation version;
* status;
* failure/staleness diagnostics.

The chart, table and Results tab should all resolve to the same version.

This prevents situations where one request sees the newly finalized game while another still sees MTM based on the previous game state.

If the existing schema already has an appropriate period/snapshot concept, extend it rather than creating a redundant table.

⸻

4. Reuse the existing conditional valuation machinery

The full simulation already produces conditional expected payouts for upcoming games.

Use those values for immediate post-game revaluation.

Conceptually:

Before the game:

official/current MTM = E[payout]

After outcome X becomes final:

live MTM = E[payout | outcome X]

For multiple games finalized since the source simulation, use the existing mechanism only if it can correctly condition on the combined realized state.

Important implementation check:

If the current conditional rows only support one-game-at-a-time conditioning from the original simulation, do not naïvely chain independent adjustments.

Instead:

* determine whether sequential conditioning is mathematically supported by the stored path/conditional data;
* if yes, apply outcomes in deterministic order;
* if not, mark the live MTM as requiring a full recalculation once more than one unresolved conditioning step accumulates.

Do not invent additive $EV swing arithmetic if it is not equivalent to conditioning the simulation.

⸻

5. Separate official simulation MTM from current live MTM

Keep both values.

Example data model:

official_mtm

* generated by latest successful full simulation;
* immutable for that simulation snapshot.

current_mtm

* starts equal to official MTM;
* changes as finalized games are incorporated;
* remains linked to its source simulation.

The UI normally displays current_mtm.

The underlying official value should remain available for:

* audit;
* history;
* “change since last full mark” calculations;
* explaining the source of live movement.

Do not overwrite the full-simulation valuation rows with provisional numbers.

⸻

6. Publish actuals + MTM atomically

This is the most important implementation requirement.

A refresh that contains a newly finalized game should not expose:

* new realized points with old MTM;
* new MTM with old realized points;
* chart using one state and table using another.

Suggested flow:

1. fetch all external data;
2. calculate new actuals in memory/staging;
3. calculate live MTM from the same game state;
4. validate outputs;
5. begin one database transaction;
6. persist actuals;
7. persist live MTM/version metadata;
8. mark that version current;
9. commit.

Only after commit should API readers see the new state.

If the current schema makes one DB transaction impractical, use a single version/status record and do not make that version readable until every component is complete.

⸻

7. Failure policy

There are two materially different failure cases.

A. External actuals refresh fails

Do not change either actuals or MTM.

Continue showing the previous coherent state and flag the refresh failure.

B. Actuals are valid but live MTM calculation fails

Do not silently show new actuals beside MTM that appears current.

Preferred behavior:

* retain the last valid MTM;
* persist/serve the newly realized actuals only if product requirements require them immediately;
* explicitly set MTM status to stale or pending_recalculation;
* expose the source actuals version and the fact that MTM does not yet incorporate it.

If feasible, stronger behavior is to hold publication of both until both are valid.

At minimum, the UI must clearly distinguish the mismatch.

Never substitute zero MTM or partially populated valuations.

⸻

8. Make refreshes idempotent

Calculate a deterministic representation/hash of the economically relevant actuals state.

If the latest refresh produces the same state:

* do not create another live-MTM version;
* do not rewrite valuations;
* do not generate duplicate history;
* return the existing current version.

A corrected game should produce a new version because its state hash changes.

⸻

9. Update all UI surfaces to use the shared current-MTM endpoint/model

Live Tracker bar chart

Bar value and sorting should use current_mtm.

If a game finalization changes MTM, the chart should update on the same refresh as the rest of Live Tracker.

Live Tracker table

Use the exact same returned valuation objects/version as the chart.

Do not separately request or calculate MTM.

Results tab

Replace any direct “latest full simulation” MTM lookup with the shared current-MTM resolver.

Results should therefore show the same current MTM as Live Tracker.

Results can separately display realized Calcutta economics, but its MTM column must come from the canonical current-MTM model.

Owner/portfolio views

Aggregate the current team MTMs after applying ownership positions.

Do not aggregate from a different snapshot source.

MCP/API

Any endpoint described as “current MTM,” “latest update,” portfolio value, etc. should use the same current valuation version.

⸻

10. Return a version ID in the relevant API responses

Every response containing actuals or MTM should include something equivalent to:

* valuationVersionId
* sourceSimulationSnapshotId
* actualsAsOf
* mtmAsOf
* markType
* stale
* staleReason

This allows the frontend to verify that chart/table/Results data refer to the same state.

If multiple HTTP requests are still necessary, the frontend should reject/mask mixed-version responses and refetch rather than render inconsistent values.

Prefer returning related data in one response where practical.

⸻

11. Define what happens after a full simulation refresh

A successful new full simulation should become the new anchor.

When full simulation snapshot N+1 publishes:

* official_mtm becomes N+1;
* reset/rebase live conditional state against N+1;
* games already incorporated into N+1 must not be applied again;
* current MTM initially equals N+1 unless additional games finalized afterward.

This must prevent double-counting a finalized game first through live conditioning and later through the new simulation.

Use game/result IDs or an explicit simulation as_of boundary to determine what the full simulation already contains.

⸻

12. Validation before making a live version current

Reuse the publication invariants already added for official snapshots where applicable.

At minimum validate:

* every expected team is present exactly once;
* all MTMs are finite;
* values are nonnegative where required;
* ownership aggregation reconciles;
* live/provisional payouts still reconcile to the pool where that invariant should hold;
* source simulation exists and is successful;
* all conditioning events actually occurred after the source simulation’s state;
* no game is incorporated twice;
* actuals and valuation version refer to the exact same finalized-game set.

If validation fails, do not promote the new live version.

⸻

13. Tests to add

Single finalized game

Start from official mark A.

Finalize one game.

Verify in one refresh:

* actuals change;
* current MTM changes;
* Live Tracker chart shows new MTM;
* Live Tracker table shows the identical MTM;
* Results shows the identical MTM;
* owner totals reconcile;
* API/MCP returns the same version.

Duplicate polling

Run the same actuals refresh again.

Verify:

* no new valuation version;
* no MTM movement;
* no duplicate actuals processing.

Corrected final score

Change a previously finalized result.

Verify:

* a new actuals/live version is created;
* prior live impact is not double-counted;
* all surfaces move to the corrected state together.

MTM calculation failure

Force conditional valuation failure.

Verify:

* no partial/live valuation becomes current;
* previous valid MTM remains;
* stale/pending status is surfaced everywhere.

Full simulation after live adjustments

Apply a live game adjustment, then publish a new full simulation containing that game.

Verify:

* new simulation replaces the old anchor;
* the game is not applied twice;
* current MTM equals the new simulation mark until another game resolves.

Concurrent reads during refresh

Verify readers get either:

* complete version N, or
* complete version N+1,

never a mixture.

⸻

Suggested implementation order

Phase 1 — Server/read-model consolidation

1. Identify the existing authoritative actuals refresh workflow.
2. Identify the current provisional/conditional MTM calculation.
3. Create one shared current MTM resolver.
4. Make Results, Live Tracker and API/MCP use it.
5. Add version/source metadata.

Do this before changing trigger behavior.

Phase 2 — Couple actuals and valuation

6. Extend actuals refresh to detect economically relevant game changes.
7. Invoke live MTM recalculation from that workflow.
8. Persist actuals + valuation under one coherent version.
9. Add idempotency.

Phase 3 — Publication safety

10. Add atomic promotion/status transition.
11. Add stale/pending behavior for failed live valuation.
12. Add rebasing logic when a new full simulation becomes official.
13. Add the validation invariants.

Phase 4 — UI

14. Point Live Tracker chart and table to the same response/version.
15. Point Results MTM to that same current mark.
16. Update owner totals.
17. Show mark type/as-of/stale state consistently.

Phase 5 — Regression tests

18. Add all tests above.
19. Verify one finalized game moves every surface identically.
20. Verify a new full simulation correctly resets the live anchor.

Do not modify the v3 football-model/calibration work as part of this task. This is a state-management/publication/read-model change around the existing official and conditional valuation outputs.
