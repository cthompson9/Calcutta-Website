Here's how I'd structure it. Four layers: Calcutta → periods (sport template) → team entries → per-period snapshots with a `basis` discriminator.

**1. Calcutta and sport-period template**

```sql
calcuttas (
  id, name UNIQUE,        -- "Calcutta XII"
  year, sport,            -- 2026, 'NFL'
  is_cannon BOOLEAN
)

sport_periods (
  id, sport, seq,          -- NFL: 0–22
  label,                   -- 'Week 7', 'Divisional'
  is_playoff BOOLEAN,      -- drives the 2x
  UNIQUE (sport, seq)
)
```

Periods belong to the *sport*, not the Calcutta — every NFL Calcutta gets the same 23, March Madness gets its 10. If a future Calcutta needs custom periods, add an override table later; don't build it now.

**2. The key design move: one snapshot table, `basis` column**

Instead of parallel realized/MTM columns (wins vs. projected_wins, playoff_berth vs. playoff_prob...), store one row per (entry, period, basis):

```sql
team_period_snapshots (
  id,
  entry_id,                -- FK to calcutta team entry
  period_id,               -- FK to sport_periods
  basis ENUM('realized','mtm'),
  wins NUMERIC,            -- realized: 4 ; mtm: 10.4
  losses NUMERIC,
  ties NUMERIC,
  pt_diff NUMERIC,
  playoff_berth NUMERIC,   -- realized: 0/1 ; mtm: 0.68
  div_round NUMERIC,
  conf_round NUMERIC,
  sb_berth NUMERIC,
  win_sb NUMERIC,
  UNIQUE (entry_id, period_id, basis)
)
```

The trick is that realized values are just the degenerate case of MTM: a clinched berth is probability 1.0, 4 wins is expected wins with zero variance. Making every metric NUMERIC means both bases share one column set, one write path, and — critically — one return formula. Realized gross return and MTM return stop being two calculations that can drift; they're the same function evaluated on different rows.

**3. Derive returns, don't upload them**

Your earlier review already flagged that `realizedReturn` is stored as an uploaded value. This redesign is the moment to fix it. Add a payout rules table per Calcutta:

```sql
payout_rules (
  calcutta_id,
  metric,                  -- 'win', 'pt_diff', 'playoff_berth', ...
  dollars_per_unit NUMERIC,
  playoff_multiplier NUMERIC DEFAULT 2.0
)
```

Then gross return = Σ (snapshot value × rate × multiplier where applicable), computed at read time or materialized per period. Same formula against `basis='realized'` gives gross return; against `basis='mtm'` gives MTM return. Commissioners upload facts and probabilities; the app owns the money math. That also kills a whole class of reconciliation bugs — a mistyped `realizedReturn` can't disagree with the win column because it doesn't exist.

**Migration notes**

- Your current results table becomes a single snapshot at the final period with `basis='realized'` for one seeded Calcutta row. Backfill is mechanical.
- The signed-ownership invariant (team sums to 100%) keys off the entry, so it's untouched — ownership stays per-Calcutta-team, snapshots are per-period.
- Add the same season-lock/transaction boundary to snapshot writes that you just built for everything else, with the unique constraint above as the idempotency backstop.

One thing to decide before building: is the 2x always "playoff periods double" or can it vary by Calcutta (isCannon interaction)? If it varies, put the multiplier on `payout_rules` per Calcutta as shown, not on `sport_periods`.
