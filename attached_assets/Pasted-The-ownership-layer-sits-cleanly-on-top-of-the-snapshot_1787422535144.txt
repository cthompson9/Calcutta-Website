The ownership layer sits cleanly on top of the snapshot design. The naming needs care because "team" now means two things — the NFL/NCAA franchise being auctioned, and the bidding entity. I'd hard-separate them in the schema:

**1. Identity layer (global, spans Calcuttas)**

```sql
consortiums (
  id, name UNIQUE          -- persistent across years/sports
)

bidders (
  id,
  consortium_id FK,
  name,
  UNIQUE (consortium_id, name)
)
```

Consortiums and bidders live *outside* any Calcutta. That's the whole point — cross-Calcutta, cross-sport, cross-year rollups only work if "Consortium X" is one row that Calcutta XII, March Madness 2027, etc. all reference. Don't scope bidders to a Calcutta; scope their *positions* to one.

**2. Position layer (per Calcutta)**

```sql
positions (
  id,
  entry_id FK,             -- the auctioned franchise entry in one Calcutta
  bidder_id FK,
  pct NUMERIC(9,6),        -- signed: can be negative or >1.0
  source ENUM('primary','trade'),
  cost_basis NUMERIC,      -- dollars paid (negative for short proceeds)
  trade_id FK NULL,
  UNIQUE (entry_id, bidder_id, source, trade_id)
)
```

This preserves the distinction you already enforce: primary auction splits stay 0–100% and sum to exactly 100% per entry; the trade ledger is what creates signed effective positions. Effective ownership is `SUM(pct)` grouped by (entry, bidder), and the invariant from your data-safety task carries over unchanged — per entry, the signed effective total must equal exactly 100%, checked at the transaction boundary, not per-row.

**3. Returns become pure joins**

Because gross/MTM returns are now derived per (entry, period, basis), owner returns need no new stored values at all:

```
bidder return (period, basis) =
  Σ over entries: effective_pct(entry, bidder) × entry_return(entry, period, basis)

bidder net = bidder gross − Σ cost_basis
consortium return = Σ over its bidders
cross-Calcutta rollup = Σ over positions in any Calcutta, since
  consortium → bidder → position → entry → calcutta is one join path
```

A short position falls out naturally: negative pct × positive team return = negative contribution, and the offsetting long shows up on whoever holds it. No special casing.

**Two decisions to make before building:**

**Cost basis and time-varying ownership.** If a bidder buys 25% via trade in Week 9, do their MTM returns reflect that position only from Week 9 forward, or retroactively? If period-accurate P&L matters, add `effective_from_period_id` to positions and compute each period's return against ownership *as of that period*. If you only care about current-state returns, skip it — but decide now, because retrofitting period-aware ownership after trades exist is painful.

**Whether consortium membership can change.** If a bidder could ever switch consortiums, today's schema silently rewrites history — last year's rollups would move with them. If that's even remotely possible, make membership a dated link table (`bidder_consortium_memberships` with from/to). If consortiums are permanent teams-of-people, the simple FK is fine.

One more carry-over: the "primary ownership can't be replaced after an approved trade" guard you built should attach to `positions` where `source='primary'` — same rule, new table.
