# Calcutta MCP V2 — Backend/API Specification

## Purpose

This document defines the V2 agent-facing API for the NFL Calcutta application.

The goal is to allow an AI agent to answer questions such as:

* "What teams do I own?"
* "What's my Calcutta portfolio cost?"
* "How is my portfolio doing?"
* "What games matter most to me this week?"
* "What's the EV swing of the Jets/Lions game?"
* "How much would a Jets win be worth to me?"
* "Which of my teams has the best current value?"
* "What am I rooting for this weekend?"
* "What's my expected payout?"
* "Which games are most important to the Calcutta?"
* "What's the biggest Marquee game?"
* "How much does the 2x point-differential multiplier matter?"
* "What is the current points rubric?"

The API should be designed so that the AI does NOT need to reconstruct relationships by making dozens of individual team queries.

The backend/database should perform joins, aggregation, and calculations whenever possible.

---

# 1. Core Design Principle

## Do not make the AI act as a database join engine.

Bad:

```text
get_team_owner1(team 1)
get_team_owner1(team 2)
...
get_team_owner1(team 32)

get_team_owner2(team 1)
...
```

Good:

```text
get_owner_portfolio(owner="Craig Thompson", season=2026)
```

The server should perform the database joins and return the complete portfolio.

This is both:

1. Faster
2. More accurate

The San Francisco 49ers omission in the previous portfolio lookup is exactly the type of error this architecture is intended to prevent.

---

# 2. Data Layers

V2 should conceptually contain five layers:

1. Calcutta ownership / financial data
2. NFL schedule
3. NFL game market data
4. Calcutta rules / points rubric
5. Projection / EV calculations

Some of these fields do not currently exist in the database.

That is acceptable.

Implement missing fields as nullable database fields or placeholder values rather than blocking the API design.

The API contract should be established now so the database can be upgraded incrementally.

# 6. Marquee Game Logic

This is a critical Calcutta-specific rule.

A game is a Marquee Game when it kicks off outside the normal Sunday 1:00 PM–7:00 PM ET window.

The Calcutta awards a 2x multiplier on point differential for Marquee Games.

The calculation must be based on the scheduled kickoff time in Eastern Time.

## Definition

```text
Normal Sunday window:

Sunday
1:00 PM ET <= kickoff < 7:00 PM ET
```

Anything outside that window is Marquee.

Therefore:

```text
if kickoff_day != Sunday:
    is_marquee = true

else if kickoff_time < 13:00 ET:
    is_marquee = true

else if kickoff_time >= 19:00 ET:
    is_marquee = true

else:
    is_marquee = false
```

Then:

```text
is_marquee == true
    => point_diff_multiplier = 2.0

is_marquee == false
    => point_diff_multiplier = 1.0
```

IMPORTANT:

Do not determine Marquee status based on:

* TV network
* "primetime" label
* national broadcast
* game importance
* betting line
* team popularity

It is purely a function of scheduled kickoff date/time.

# 7. TBD Kickoff Logic

If kickoff time has not yet been announced:

```text
kickoff_at = null
is_marquee = null
point_diff_multiplier = null
```

Do NOT assume TBD games are Marquee.

When the NFL announces the time, update the game and recalculate:

```text
is_marquee
point_diff_multiplier
```

This is particularly important for Weeks 16–18.

# 14. Moneyline → Implied Probability

For American odds:

Positive:

```text
implied_probability = 100 / (moneyline + 100)
```

Negative:

```text
implied_probability = abs(moneyline) / (abs(moneyline) + 100)
```

Raw implied probabilities contain sportsbook vig.

If useful, calculate no-vig probabilities:

```text
raw_home_prob = ...
raw_away_prob = ...

total = raw_home_prob + raw_away_prob

no_vig_home_prob = raw_home_prob / total
no_vig_away_prob = raw_away_prob / total
```

Store both if possible.

---

# 15. Win Probability

Do NOT equate sportsbook implied probability with the application's projection.

There should be two concepts:

```text
market_implied_probability
model_win_probability
```

For example:

```text
market:
DET 73.7%

model:
DET 69.0%
```

The model probability should come from a projection model.

Initially:

```text
model_win_probability = null
```

is acceptable.

Do not invent probabilities.

# 26. EV Definition

The backend should distinguish:

## Outcome value

Value of the portfolio if Team A wins.

## Expected value

Probability-weighted value across outcomes.

For a simple two-outcome game:

```text
EV =
    P(A wins) * portfolio_value_if_A_wins
  + P(B wins) * portfolio_value_if_B_wins
```

For incremental EV relative to the current state:

```text
EV_change =
    P(A wins) * change_if_A_wins
  + P(B wins) * change_if_B_wins
```

## EV swing

Define:

```text
EV_swing =
    change_if_A_wins - change_if_B_wins
```

This is useful for answering:

> "How much does the Jets/Lions game swing my portfolio?"

---

# 27. IMPORTANT: Do Not Double Count

The EV engine must not simultaneously count the same value through:

* current MTM
* points
* payout
* projected payout

unless those quantities are explicitly defined as separate stages.

The backend should document whether MTM represents:

```text
current estimated liquidation value
```

or:

```text
projected payout
```

before using it in EV calculations.

---

# 28. Marquee Game EV

The Marquee multiplier must be applied specifically to point differential.

Conceptually:

```text
regular_point_diff_value =
    point_differential * point_diff_value

marquee_point_diff_value =
    point_differential
    * point_diff_value
    * 2
```

Do NOT multiply:

* win points
* playoff points
* Super Bowl points
* all game EV

by 2.

The multiplier applies only to the point-differential component.

```text
snapshot_at
```

This allows the agent to say:

> "The current line is..."

versus:

> "The line was..."

and prevents stale data from being treated as current.

---

# 40. Source Precedence

Recommended precedence:

### Schedule

1. NFL official schedule
2. manually verified schedule data
3. cached application schedule

### Betting market

1. configured sportsbook/odds provider
2. secondary configured provider
3. cached market snapshot

### Calcutta ownership

1. current approved ownership state
2. original auction ownership
3. pending trades should not override approved state

### Calcutta rules

1. database rules table
2. authoritative Calcutta configuration
3. Markdown documentation as explanatory fallback

The Markdown should explain the rules but should not silently override authoritative database configuration.

# 43. Required Validation

The backend should validate:

### Games

* home team != away team
* valid NFL team
* valid season
* valid week
* one game cannot have duplicate home/away pairing for the same week

### Probabilities

```text
0 <= probability <= 1
```

and:

```text
home_probability + away_probability = 1
```

within a small numerical tolerance.

### Marquee

If:

```text
kickoff_at == null
```

then:

```text
is_marquee == null
point_diff_multiplier == null
```

Otherwise calculate deterministically.

# 44. Important Agent Behavior

The AI should never:

1. Guess missing data.
2. Enumerate all NFL teams to determine ownership when `get_owner_portfolio` exists.
3. Treat market-implied probability as model probability.
4. Treat TBD kickoff times as Marquee.
5. Apply the Marquee multiplier to anything other than point differential.
6. Use pending trades as current ownership unless explicitly instructed.
7. Assume MTM equals projected payout.
8. Present placeholder values as actual values.

# 46. Key Architectural Principle

The MCP should expose **agent-level concepts**, not merely database columns.

The AI should be able to ask:

```text
get_owner_portfolio
get_game_ev
get_owner_game_leverage

```

rather than having to understand the database schema and manually join:

```text

games
markets
projections
rules
period_snapshots

```

The backend should do those joins.

The AI should do the reasoning and communicate the result.
